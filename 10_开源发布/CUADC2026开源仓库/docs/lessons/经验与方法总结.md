## 一、分层隔离排障法

**是什么**：当系统由多个环节串联（供电→接线→参数→固件→软件→链路）时，不靠猜测替换部件或改配置，而是逐层隔离故障域，每次只改变一个变量，用可控实验收窄嫌疑。

**为什么**：

- 09-18 舵机 A2 不动，若直接换舵机或改参数会走弯路。实际用「供电、信号链、本体三段排除法」：先证明 A1 同轨动作→供电无嫌疑；再回读 PWM 全绿→信号链无嫌疑；最后重插插头动作→定位虚插。
- 09-10 仿真模型全部不加载，用「单变量 A/B 对照」：完全相同命令仅资源路径一个带尾分号一个不带，0 个 vs 12 个模型话题，锁死根因。
- 09-25 GPS 零星排查中，先排除「室内没天空」再查「射频链路断」，用 MON-RF 判天线在位、NAV-PVT 判收星，最终定案为纯环境屏蔽而非硬件故障。
- 10-06 夜航位置链断流（odom 断流触发 MISSION_FAILURE 转 LAND），10-07 SD 卡 4K 随机写 155 IOPS 定罪弱卡：按「GPS 掉线→EKF 异常→SD 卡弱写」逐层排序，每次只改一个因素，最终定位弱 SD 卡拖垮主循环饿死 GPS 驱动。

**怎么做**：

1. 画出链路拓扑，明确各层边界（供电、物理、协议、参数、软件）。
2. 用探针或回读建立每层的健康判据，而不是直接跳到结论。
3. 怀疑某项时，用「同线/同口/同配置」的可控交叉实验验证，一次只改一个变量。
4. 排除掉的嫌疑要留痕，避免后续排障时翻旧账。

## 二、判别式探针法

**是什么**：设计低成本、可复用的探针或监控脚本，用真实数据流或回读值来判定链路是否正常，而不是依赖 `ros2 topic echo --once`、进程名匹配或「没反应」这类不可靠信号。

**为什么**：

- `ros2 topic echo --once` 因 DDS 发现延迟和假阴性，至少四次重复咬人：09-09 首证误判连接失败、09-10 复发、09-12 探测 40s 仍假阴性（11 册三次实证）、10-04 仓库闸门脚本自身第三次应验（当日叠加 ros2 daemon 僵死）。最终统一改为「流式读取 + 任务状态节点日志」作为真实判据。
- `pkill -f` 自匹配杀伤 SSH 会话成为高频事故，从 09-06 首犯到 09-26 再犯、10-04 多次复发，教训是清理进程必须用 `[x]` 括号技巧或 PID 直杀。
- 09-17 GPS 排查中，用 `fix_type` 区分「无通信(0)」与「搜星中(1)」，避免误判硬件故障；10-07 用 RCOU+CTUN 勘误 203 号日志（「Stab 22 分钟练习」实为电机怠速误记）；09-26 的同族教训是误把一次悬停当全部飞行，重读日志才发现 10+ 个解锁段。
- 09-12 用 `fcu_ready` 心跳连续稳定窗门禁，取代了被动等待 15~20 分钟的不稳定窗。

**怎么做**：

1. 优先使用链路自身的可观测信号：MAVLink 心跳、dataflash 日志、SERVO_OUTPUT_RAW 回读、任务日志 STATE 轨迹。
2. 所有探针必须验证其本身的可靠性——例如先用已知有流的口反证嗅探机制。
3. 判据要闭环：写入后独立回读，不信 ACK；链路活性看流式帧，不信 `--once`。
4. 把好用的探针固化成脚本（`check_rng.py`、`check_can.py`、`fc_link_test.py` 等），下次复用。

## 三、SSOT 单一事实源制度

**是什么**：全项目只保留一份权威方案文档（SSOT），所有改方案、参数、结构的行为都必须先落到 SSOT，再辐射到代码、yaml、说明书、操作卡。旧文档、教程、备份、日志都只是历史，不得重新成为权威。

**为什么**：

- 09-05 之前四份设计文档 + 训练任务书并存，类别表出现旧 GHS 9 类与附件 11 十类冲突，导致标注和数据反复返工；当日建立 `总体方案与执行计划.md` 作为唯一权威，旧文档归档，才收敛了多口径。
- 09-14 PLND_TYPE 两个文档互相矛盾（§4.5=1 与 §11=0），根源就是未把 ArduPilot 实际枚举核对后统一写入 SSOT；09-18 起按 AGENTS 规则 1 执行「以 SSOT + 最新日志为准、旧文档一律不改写」。
- 09-25 全仓三方对账审计（252 受管文件×71 提交×日志 39 节）发现「翻案残留模式」：每次只改主结论行，排障表/台账/检查表边角留旧口径，grep 实证一次捞出 19 处。之后立下「每踩一坑即回写坑清单」和「SSOT 文档地图逐行存在性验证」两道防线。
- 10-05 按旧基线修复 FLTMODE6 把它「修回」RTL，与 10-04 已拍板的 Guided 冲突，直接原因是「基线过期误修」，本质是未把最新拍板同步到 SSOT 与基线。

**怎么做**：

1. SSOT 必须是具备「入口 + 修订状态 + 逐行可验」的文档，并登记在根 README 地图中。
2. 改方案先改 SSOT，再同步代码、yaml、说明书、操作卡；文档中凡与实现不一致处必须显式标注「以回读为准」。
3. 历史日志、归档文档、第三方教程一律不改写，但在 SSOT 中挂勘误链，防止以旧压新。
4. 所有新文档产出后 24 小时内必须登记到 SSOT 文档地图，否则视为孤儿资产。

## 四、闸门回归制度

**是什么**：任何代码/参数/模型变更，在真机或生产环境生效前，必须通过一道可复现的验证闸门——从静态语法检查，到单元测试，到 SITL 全链路回归，再到台架 A/B，逐层放大风险，未过闸不得上真机。

**为什么**：

- 09-07 就立下「SITL 不过不上真机」铁律，10-06 写入 SSOT §7、10-08 起每批强制执行的「每版代码先过 SITL 回归再上真机」，因为 10-05 起飞命令被 FC 静默拒绝三天，就是 SITL 家海拔 0 盲区掩盖了 MSL 参考系 bug。
- 09-20 建立了 `fc_regression_m3.sh` 四段式自动判定闸门（colcon build → 单测 → reset_sim → 全任务判分），并在 09-25 三跑中先拦死锁、再拦真值漂移、三跑 PASS 放行。
- 10-01 模型换产采用「台架 A/B 五判据全过才换模」，防止 val 指标虚高掩盖真机域泛化失败（09-28 v4 机载域「空景 24 帧零检出、靶标仅低置信（≤0.29）且类别判错」就是反例）。
- 10-08 改进落地判据、角速度门控、GNSS 载体判据等所有代码改动，都标注「未编译未过闸」，直到 `fc_sitl_m3.sh` 连续两跑 REGRESSION PASS 才放行。

**怎么做**：

1. 闸门必须一键可跑、结果机械判定（全过输出 PASS，任一 fail 中止）。
2. 回归用例覆盖真实场景盲区：SITL 家海拔≠0、随机布景、故障注入。
3. 每个改动批带「进入条件 / 退出条件 / 回归判据」，未过闸只允许在台架或 SITL 环境内实验。
4. 换模型换权重，必须先在影子槽（如 `~/v3_shadow/`）构建，经台架 A/B 五判据后，才写入生产 `~/cuadc_models/`。

## 五、防呆固化

**是什么**：把高频犯错的坑，用脚本、断言、勾选清单、家规、自动化检查等形式固化成机器可执行的防线，让同一类错误无法再犯。

**为什么**：

- 09-11 前反接烧模块风险，升级为「任何新线缆上电前必过万用表两头逐针」家规（复训实证：09-15/09-22/09-26）。
- 09-12 写参数后立即重启导致 IST8310 External 丢失翻案，立下「写参数后等 5 秒再重启」铁律。
- 09-26 两次 CRLF 事故（systemd 服务重启循环、投放脚本 CRLF）后，固化「推脚本前后必查行尾」。
- 09-19 建立 `load_params.py` 参数导入脚本化两遍+回读，替代 MP 手点，防止漏项。
- 10-01 标注修正脚本内置「恰 10 框十类各一」硬断言，两次拦下目检误判。

**怎么做**：

1. 每次事故的根因都要提炼成一个「防呆规则」，并在 24 小时内写入工具、脚本、操作卡或 AGENTS.md。
2. 防呆规则做到强约束：脚本内断言 + 写盘前校验 + 运行前检查卡，而不是只靠记忆。
3. 用「只推不拉、哈希对账、白名单级 gitignore」等机械纪律代替人工核验。
4. 定期回归防呆规则本身的有效性——比如 pkill 方括号技巧是否真正执行。

## 六、台账与勘误链

**是什么**：对参数备份、文档版本、错误结论、认知翻转建立持续更新的台账，记录「为什么」「错在哪」「更正是什么」，让历史教训不出第二次。

**为什么**：

- 09-26 参数备份原只有时间戳，同一天 8 份备份无法区分「为什么改」；建立 `changes.md` 逐份补缘由与证据指针后，才可追溯。
- 11 册勘误链首条为 RTK-01-R 针序翻转（09-11 接错、09-15 实锤旧文档针序本身错误），PLND_TYPE 写错在 09-05、09-14 勘正，末条 09-26 记录 Re0 教程 v11 源码事实≠现行三包，共 13 条，成为后续排障的第一检索入口。
- 09-25 排障节与 11 册曾写「MON-RF/MON-HW 被桥接屏蔽」，同日会话内实测 MON-RF 轮询有应答（仅 MON-HW 被拦），当场勘误并关闭旧结论。
- 10-05 参数漂移三犯后，`bbb4107` 结论被推翻，靠的是对比快照与台账，而非重新猜。

**怎么做**：

1. 参数备份、固件、文档、结论，所有可能翻案的条目都必须落到一个「可检索、可对比」的台账中。
2. 改动记录要含「原因 + 证据指针 + 时间戳」，而不是只有文件名。
3. 勘误链条目必须以「旧口径 → 现行口径 → 证据」三元组形式，并保证只在现行文档引用，历史文件冻结。
4. 每周或每次参数漂移事件后，扫一遍台账，确认没有「新结论被旧结论覆盖」。

## 七、AI 协作契约

**是什么**：如果团队重度借助 AI 编程与排障，必须为 AI 会话立下独立规则层（如 AGENTS.md），规定 AI 可做什么、不可做什么、如何复核产出，并把「先查 SSOT、先 dump 字段、先跑 grep 实测」固化为 AI 工作前置动作。

**为什么**：

- 09-08 AI 凭记忆给错 Quad X 方向表，导致用户相线对调返工；同日后查 ArduPilot 源码才定案。教训是：任何枚举、方向、映射一律查源码或实测，不凭记忆。
- 09-17 全库重构后，发现仓库重度 AI 协作但无 AI 规则手册，建立 `AGENTS.md` 六条红线（SSOT 唯一、日志只追加、白名单严禁放宽等），此后违规提交与误操作明显收敛。
- 09-20 AI 仅用 grep 宏判决「零测试」，实为自写断言式用例 29/66 例；深探查到 file:line 才修正结论。
- 09-30 凌晨 AI 幻觉编造 git 输出，当即停下并让用户验证，之后立下「工具输出不可信时暂停操作」的默契。

**怎么做**：

1. AGENTS.md 至少包含：权威文档指针、禁改区（归档/参考仓/第三方）、日志只追加、白名单不得放宽、结构变更双同步、飞控/接线安全边界。
2. AI 产出必须经过「先 grep 实证、再 file:line 定位、再改」三步，未经实证的结论必须带「猜测」标记。
3. 多会话并行时，每个会话只提交自己 hunk，不代提并行内容；共享文件用「HEAD 基准分块暂存」。
4. 用户需求变更或指令不清楚时，AI 应当先问，不得自行按推荐口径定案并伪装成用户已拍板。

## 八、数据闭环（采集 → 训练 → 台架 A/B → 上线）

**是什么**：视觉/模型类工作必须形成从数据采集、标注、训练、部署、台架 A/B 到生产切换的完整闭环，每个环节有审计与验收，尤其强调「真机域」样本必须进入验证集。

**为什么**：

- 09-28 v4 模型在训练 val 上全绿，上台架在机载相机域空景零检出、靶标仅低置信且类别判错，根本原因是「val 与训练同域同渲染」未暴露相机色域偏移 13°。之后固化「val 必须掺机载直采帧」。
- 09-05 连续帧随机切分泄漏，导致 mAP 虚高；改为按视频片段整段切分后，09-12 建集继续按片段防泄漏，并加 `--pin-train` 参数钉死特定片段。
- 10-01 换模 v3.1 → v3.2 时，必须先归档 v2 三件（engine/pt/onnx）防覆盖；台架 A/B 五判据含新摆位 1.5 牌、双牌不互串、十牌扫测、空景误报、FPS。
- 09-30 同步清单混入 `.pytest_cache` 垃圾、09-28 部署脚本旧版漏同步，形成「repo→Jetson 单向清单化 md5 对账、只推不拉」教训。

**怎么做**：

1. 采标训三环节用同一套类别表（以附件 11 实表为 SSOT），旧表数据一律重映射后使用。
2. 建集脚本内置审计器，只报告不改标签，双 split 全 PASS 才训练。
3. 训练验收分「老域零退步 + 新域单列」双指标，避免新域稀释掩盖退化。
4. 模型上线必须走「影子槽构建 → 真机台架 A/B → SHA 强校验 → 生产切换」四步，生产槽永远保留回退文件。

## 九、安全红线制度

**是什么**：凡涉及电机、舵机、供电、飞行、投放的操作，设立不可妥协的铁律，写成操作卡/家规/AGENTS.md 红线，并配套验证手段让违规可被机械阻止。

**为什么**：

- 09-30 161 号飞行在 6.8m 空中按 RC6 急停，四电机断电自由落体摔机；当日日志已提过「急停只许 <0.5m」但未形成有效防呆，10-07（199#8、203 号）与 10-08（233/234/235 号三连）接连重演。最终立下「空中中止用 LAND，EStop 仅限地面/<0.5m」铁律，并在操作卡双重标注。
- 09-08 电机测试必须拆桨，10-03 再次用例，已成为 AGENTS.md 硬规则。
- 09-15 SIH 台架铁律「SIM_OH_MASK 开了就按电机会转对待，必须拆桨；SIH 固件只上台架禁外场」防止了仿真固件与真机参数混淆。
- 10-10 反盲投铁律（10-09 为盲投模式定案日，该模式次日已整体回退）：目标不新鲜或无视觉跟踪，绝不按旧坐标盲投——来自 HIT 区赛教训，并在 M3 门控中贯穿 `target_age≤0.5s` + 弃桶机制。

**怎么做**：

1. 安全红线必须同时写进「操作卡 + 脚本门禁 + 代码 fail-closed + AGENTS.md 红线」四层，且默认值取最安全态。
2. 涉及动力或载荷的操作，必须有「拆桨、拆弹、单通道隔离、倒计时、安全开关在位」等前置检查，并令脚本自动核验（如 motor_test 三道核验）。
3. 被绕过的安全自检（如 ARMING_SKIPCHK=1280）必须在显式位置标注「台架用，户外前恢复全身检查」，并纳入上场前回读清单。
4. 空中异常处置路线（切 PosHold/LAND 而非 EStop）要写进飞手培训卡，每次飞行后复盘是否有违规。

## 十、同名异构与版本锚点防护

**是什么**：遇到同名但内容不同的文件（脚本、yaml、模型、参数）时，不按文件名复制或引用，必须用精确路径 + 哈希 + 功能标识区分，并锁定版本锚点避免漂移。

**为什么**：

- 10-04 仿真判分桥 11 行同名 `mission_params.yaml` 被 `cp` 按名覆盖成真机版，导致后续仿真判分错乱；从 Jetson src 恢复后才各归各位。
- 09-25 真值文件 `generated_scene.yaml` 与 `judge_truth_params.yaml` 漂移，二跑判 0 分，其实是旧随机布景残留，不是算法问题。
- 10-01 `bench_trt.py` 固定 640 输入，832 引擎断言失败；`test_one_target.py` 对照 engine 停在 v4 旧路径，都是版本未参数化或未同步。
- 09-16 SIH 编译 pin 到 dbe79216，类名 `MultiCopter` 大写 C，换 master 或凭记忆都会编译失败。

**怎么做**：

## 给下一届/其他队伍的 20 条最值钱经验

1. 串口连不上先扫端口、拔插 USB，不要急着判变砖（09-05）。
2. 参数写入后独立回读，不信 ACK，写完等 5 秒再重启（09-12）。
3. `ros2 topic echo --once` 不当探针，用流式+任务状态日志判活（09-09）。
4. `pkill -f` 加 `[x]` 括号或 PID 直杀，防自杀 SSH（09-06）。
5. 新线缆上电前必过万用表两头逐针（09-11）。
6. SITL 不过不上真机，闸门机械判定，一票否决（09-07）。
7. 只有一份 SSOT，改方案先改 SSOT，再同步代码/文档（09-05）。
8. 训练 val 必须掺机载真机域样本，否则台架泛化翻车（09-28）。
9. 换模型必须有影子槽构建 + 台架 A/B 五判据全过，才动生产（10-01）。
10. 模型/权重/SHA 强校验不符拒启，换模先归档旧件（09-13）。
11. 所有静默拦截必须补 WARN 日志，否则排障三天找不到原因（10-07）。
12. EStop 只限地面/低于 0.5m，空中中止用 PosHold+LAND（10-01）。
13. 拆桨后再做任何电机/舵机测试，脚本内置三道核验（09-08）。
14. 参数存入基线文件前先 export 当前态，旧基线过期会误修（10-05）。
15. 数据划分按整段片段，防连续帧跨 train/val 泄漏（09-05）。
16. 日志只追加、旧文不改写，勘误走勘误链不以旧压新（09-17）。
17. Windows 与 Jetson 换脚本文件必查 LF/CRLF，否则 shebang 炸（09-26）。
18. AI 协作要立 AGENTS.md 红线，AI 结论先 grep 实证再动码（09-17）。
19. 多会话共享仓库时，分块暂存只提交自己 hunk，不代提（09-26）。
20. 每次踩坑 24 小时内回写坑清单 + 防呆工具，坑只踩一次（09-13）。
